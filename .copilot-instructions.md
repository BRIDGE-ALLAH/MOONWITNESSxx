# MOONWITNESS // RIOTWORKS — Repository Instructions

These instructions apply to the canonical repository BRIDGE-ALLAH/MOONWITNESS. RIOTWORKS is a product division inside MOONWITNESS, not a separate repository. The current-state inventory and execution order in docs/23-repository-audit-and-current-execution-plan.md are authoritative. If an older instruction conflicts with docs/23, follow docs/23 and update the stale instruction in the same change.

## 1. Canonical repository topology

- Use pnpm and the committed pnpm-lock.yaml.
- Workspace globs are apps/* and packages/*.
- apps/headquarter is the Next.js App Router frontend.
- apps/arsy is the only Fastify HTTP backend and composition root.
- packages/ui is the shared React component library.
- packages/arsy-core is reusable Fastify lifecycle/runtime infrastructure, not a second app.
- ORM, DB runtime/adapters and ORM addons are planned until their source, exports, tests and build checks exist.
- Do not add services/* to the workspace. Existing services/arsy and services/queue are duplicate/stranded prototypes; review unique behavior before retiring them.
- An independently deployed background worker, if needed, belongs under apps/worker. Shared job contracts and queue adapters belong under packages/.

## 2. Ownership and dependency boundaries

- Headquarter may depend on UI, types and API contracts; it must not import Fastify server internals, ORM persistence, DB drivers or privileged credentials.
- ARSY may depend on arsy-core, contracts, types, ORM/database packages and enabled addons; it must not depend on packages/ui.
- ORM owns metadata, model registry, addon composition, domains, recordsets and lifecycle.
- orm-db owns transactions, unit-of-work, schema reconciliation and schema receipts.
- Concrete SQL adapters own provider drivers, introspection, mapping, DDL and provider capabilities.
- Addons declare domain models and services; never import Kysely, raw SQL or concrete DB drivers.
- Policy/ZILL is for rights, provenance, quality and platform rules; it is not the authentication/authorization engine.
- Notifications own outbound delivery. Communication/chatter owns human collaboration. Audit, domain events, outbox, activities and jobs remain distinct.

- Headquarter pages live in apps/headquarter/src/app.

## 4. Product and data truth

- Distinguish demo/synthetic data from live data in UI and APIs.
- Never simulate marketplace publication, payment, OAuth, real sales, traffic or approvals as completed.
- No guarantee of income, sales, traffic, ranking or monetization.
- Preserve provenance, licensing, evidence, financial reconciliation and auditability.
- No raw provider secrets in source, browser bundles, logs, audit diffs or ordinary records.

## 5. BaseEntity and schema policy

Every persisted ORM model receives exactly five ORM-composed fields: id, createdAt, createdById, updatedAt, updatedById. Actor fields come from trusted server execution context. Do not globally inject active, archive, soft-delete, version, workspace, company or business ownership fields.

Use code-first TypeScript model declarations and the private ARSY schema plan/reconcile/verify/status API. Routine additive model changes do not require handwritten migration files. Semantic data transformations use typed programmatic handlers. Destructive schema changes require explicit approval, verified backup and recovery plan. PostgreSQL is production target; libSQL is local/single-node. PocketBase is not a v1 dependency.

## 6. Engineering workflow

- Inspect current main, working tree and relevant docs before changes.
- Read docs/23 before selecting tasks; do not skip P0 repository repair.
- Make small dependency-ordered changes. No empty placeholder packages.
- Use explicit package exports, strict TypeScript, deterministic build order and tests.
- Every package script must point to an existing tool/source/config.
- Root CI must use frozen lockfile and fail on required lint/typecheck/test/build failures.
- Pre-commit must be local, fast and deterministic. No network AI calls, release version bumps, changelog rewrites, GitHub issue creation or blanket || true.
- Version/changelog automation runs at release time, not every commit.
- GitHub workflows must run from repository root, use pnpm, validate YAML and avoid duplicate issue creation.
- AI-generated commit messages are optional; offline fallback must work and must not create hidden/staged artifacts.
- Do not hardcode RIOTWORKS as GitHub repository name; use MOONWITNESS repository metadata/config.
- Keep README, master prompt, docs, Wiki and changelog aligned with actual code. Never describe a target as implemented without evidence.

## 7. Validation

Follow docs/24 for the automation contract. Before marking work complete, run applicable commands and report exact outcomes:
1. pnpm run lockfile:check (preserve existing lockfile edits; regenerate deliberately when stale)
2. pnpm install --frozen-lockfile
3. pnpm run validate:repo
4. pnpm run type-check
5. pnpm test
6. pnpm build

Repository audit success is not proof of application build success. Run the full package checks for affected code. If a command cannot run in the available environment, say so; do not infer success.

## 8. Change safety

Preserve existing work and inspect diffs before deleting/renaming. Root package.json, pnpm-workspace.yaml and turbo.json may be changed when necessary to repair architecture; they are not permanently immutable. Explain impact and update lockfile/workspace tests in the same change. Never overwrite unpushed local work or force-push main without explicit authorization.
