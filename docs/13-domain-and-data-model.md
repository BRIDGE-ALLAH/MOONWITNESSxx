# 13 — Domain Model, BaseEntity & AuditTrail

**Status:** Approved conceptual model  
**Version:** 1.1  
**Updated:** 2026-11-07

## 1. Design principles

- Model business objects explicitly.
- Separate framework metadata from domain fields.
- Centralize common entity fields in orm-addon-base.
- Separate active/archive lifecycle from business workflow state.
- Separate append-only audit events from mutable business records.
- Separate evidence, assumptions, and generated recommendations.
- Separate asset binaries from metadata.
- Separate channel capability from account authorization.
- Separate financial events from dashboard aggregates.
- Preserve provenance and version lineage.
- Never store raw credentials in ordinary domain tables or frontend state.

## 2. BaseEntity contract

Every persisted business model registered through the ORM receives the base entity fields automatically through ORM model composition and the installed base addon.

### Required common fields

| Field | Type | Rule |
|---|---|---|
| id | Stable ID | Generated by the configured adapter where possible |
| active | boolean | Default true; inactive records are excluded by normal listing queries |
| createdAt | datetime | Set centrally on create |
| updatedAt | datetime | Updated centrally on mutation |
| createdBy | actor reference | Set from trusted ORM environment when available |
| updatedBy | actor reference | Set from trusted ORM environment when available |
| version | integer | Optional optimistic concurrency counter where supported |

Optional central archive metadata:
- archivedAt
- archivedBy

These fields are not redefined in individual addons.

active is a lifecycle flag, not the same as a domain status. Example: Project.state = completed can coexist with Project.active = true. Archiving sets active = false; restoring sets it back to true. Hard deletion is a separate restricted operation.

The ORM should support an explicit includeInactive option. Ordinary user-facing search/list methods should filter inactive records unless the caller has appropriate permission and explicitly requests them.

## 3. AuditTrail contract

AuditTrail is implemented once by orm-addon-base and triggered by ORM lifecycle operations.

Required audit properties:
- audit ID.
- model technical name.
- record ID.
- action: create, update, archive, restore, delete, or sensitive administrative action.
- actor ID and actor type.
- timestamp.
- source: API, agent, system, import, migration, or other registered origin.
- request/trace ID.
- changed field names.
- safe before/after diff where applicable.
- reason and metadata where applicable.

Rules:
- Normal application code cannot update or delete an audit entry.
- Sensitive values and secrets must be redacted.
- Audit reads require authorization.
- Audit writes are automatic; domain addons must not duplicate the mechanism.
- Use a transaction where supported.
- If the active adapter cannot guarantee atomic mutation + audit, use an explicit durable outbox/reconciliation mechanism or reject operations that require strict atomic audit.
- Do not claim tamper-proof or immutable infrastructure unless the storage controls actually enforce it.

## 4. Base addon and model composition

packages/orm-addon-base is installed before business addons. It defines abstract base metadata and shared services.

Every persisted model is composed with BaseEntity at registry time. Addons declare only business-specific fields. Duplicate declarations of base fields should raise a registry error rather than shadowing the central definition.

Base addon may also provide shared mixins such as display name, description, ownership, and archive behavior, but only universal fields belong on every model.

## 5. Core business entities

### Workspace
Owner settings, country, timezone, currencies, preferences, limits.

### MarketSource
Source identity, canonical URL, type, access method, permitted use basis, and review status.

### EvidenceItem
Captured observation, timestamp, excerpt/summary, source reference, reliability, and privacy classification.

### Opportunity
Buyer problem, segment, job-to-be-done, channel fit, score, confidence, hard-gate state, and decision history.

### Product
Product family, buyer value, category, lifecycle, owner, and current version.

### ProductVersion
Version number, changelog, deliverables, preview, compatibility, and approval status.

### ProductionJob
Brief, factory, workflow, agent assignments, budget, artifacts, and run state.

### Asset
File identity, storage location, checksum, dimensions/format, creator, source, and metadata.

### ProvenanceRecord
Prompt/brief, tool/model, source materials, license, edits, human contribution, AI disclosure, and derivative links.

### Inspection
Rule-set version, findings, evidence, severity, reviewer, decision, and timestamp.

### Channel
Provider identity, eligible product types, countries, policies, capability level, and review date.

### ChannelAccount
External account reference, authorization state, allowed scopes, secret reference, and expiry. Raw tokens are stored only in protected secret infrastructure.

### Listing
External listing identity, product version, channel, metadata, price, status, and publication receipt.

### Workflow / WorkflowRun
Trigger, schedule, steps, permissions, input/output, cost, logs, approvals, idempotency key, and error state.

### FinancialEvent
Gross sale, commission, royalty, fee, refund, chargeback, withholding, adjustment, or payout.

### Payout
Provider, currency, amount, status, destination reference, and reconciliation evidence.

### Experiment
Hypothesis, variable, sample, period, result, confidence, and decision.

### AuditEvent
Centralized audit record created by the base ORM lifecycle; not reimplemented per addon.

## 6. ORM field and query conventions

Use declarative metadata with typed builders for string, text, boolean, integer, float, decimal, date, datetime, JSON, selection, and relation fields. Query expressions must be validated against model metadata and adapter capabilities.

Money must use decimal-safe representation or integer minor units with explicit currency. Do not use binary floating point as the authoritative money representation.

## 7. Financial ledger

FinancialEvent includes:
- Provider event ID.
- Product/listing.
- Event type.
- Gross amount.
- Fee amount.
- Refund/adjustment amount.
- Net amount.
- Currency.
- FX rate and source if converted.
- Event and payout date.
- Pending/settled/reversed state.
- Source evidence.
- Reconciliation status.

Never treat estimates or pending commissions as settled cash. Use append-only corrections instead of silently rewriting financial history.

## 8. Multi-currency and timestamps

Preserve original transaction amount/currency. Store reporting-currency conversion separately with rate, source, and timestamp. Store UTC timestamps and display in workspace timezone.

## 9. Privacy and retention

Collect only data required for the business function. Prefer aggregated community insight over profile-level personal data. Protect customer data, support export/deletion where appropriate, and define retention for source snapshots, logs, and generated artifacts.
