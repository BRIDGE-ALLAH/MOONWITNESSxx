# 15 — Roadmap & Acceptance Criteria

**Status:** Approved execution baseline  
**Version:** 1.0  
**Updated:** 2026-11-07

## 1. Delivery strategy

Build and validate the business loop in small increments. Do not build every factory or integration before proving that a real product can pass quality checks, be listed through an allowed channel, and generate reconciled results.

## 2. Phases

### Phase 0 — Product definition (current baseline)
Deliver:
- Narrative and ecosystem alignment.
- Product charter and business model.
- Marketplace portfolio and platform gates.
- Intelligence model and scoring.
- Product factory definitions.
- Autonomy and governance.
- Architecture and information architecture.
- Design DNA and design system.
- v0 master prompt.

Exit: documents are internally consistent and v0 can build the UI without inventing product scope.

### Phase 1 — v0 visual prototype
Deliver:
- ARSY DECK.
- SIGNAL ROOM.
- RIOT RADAR.
- THE FORGE.
- ZILL WATCH.
- Coherent secondary pages.
- Dark/light themes.
- Original character/graphic placeholder assets.
- Working local prototype interactions.
- Clear DEMO labels.

Exit:
- No dead navigation or buttons.
- No fake marketplace connection.
- No synthetic finance presented as real.
- Visual acceptance against docs/10 and docs/11.
- Responsive and accessible basic behavior.

### Phase 2 — MVP intelligence and product registry
Deliver:
- Workspaces and settings.
- Evidence capture with source/date.
- Opportunity records and versioned scoring.
- Product briefs and lifecycle.
- Asset library and provenance.
- QA report records.
- Audit events.

Exit: one opportunity can be traced from evidence to product version and inspection report.

### Phase 3 — First production slice
Start with one Digital Utility product family and one Stock Asset product family.

Deliver:
- Production job queue.
- Local/cloud model provider abstraction.
- File storage and artifact versions.
- Metadata package.
- Technical and creative checks.
- Manual marketplace upload packages.
- Initial cost tracking.

Exit: at least one real product package is created, rights-checked, quality-reviewed, and manually submitted by the owner.

### Phase 4 — Channel readiness and financial truth
Deliver:
- Country and payout preflight.
- Channel capability registry.
- Official integration assessment.
- Listing records and publication receipts.
- Statement/CSV ingestion where permitted.
- Fee/refund/payout reconciliation.
- MIZAN net-contribution view.

Exit: one channel's genuine financial records can be reconciled with source evidence.

### Phase 5 — Safe automation
Deliver:
- Scheduler and workflow runs.
- Approval inbox.
- Idempotent jobs.
- Budget/rate limits.
- Kill switch.
- Manual fallback.
- Official API actions only after channel-specific validation.

Exit: automation is reliable, observable, and reversible where possible.

### Phase 6 — Portfolio learning
Deliver:
- Aftershock cohorts.
- Product-level conversion and contribution.
- Experiment history.
- Improve/pause/retire recommendations.
- Policy review alerts.

Exit: recommendations use actual operator data, not demo assumptions.

### Phase 7 — Expansion
Consider Affiliate Media, KDP, workflow products, YouTube, game assets, and microgames after the core slice is stable.

## 3. First pilot scope

Recommended:
1. Original Digital Utility product, e.g. a useful small-business spreadsheet/template with documented functionality.
2. Original Stock Asset collection, with differentiated assets and accurate metadata.
3. One affiliate content experiment only after account eligibility and disclosure requirements are confirmed.

Do not start with all platforms or all factories at once.

## 4. Quality gates

### Product gate
- Defined buyer and job.
- Evidence references.
- Differentiation explained.
- Price/fee assumptions visible.
- Channel chosen for a reason.

### Rights gate
- Source rights documented.
- No prohibited IP/l likeness/trademark use.
- Commercial-use terms checked.
- AI disclosure recorded where required.

### Technical gate
- Correct formats and dimensions.
- Files open and render.
- Required components present.
- Version and manifest present.
- No malware or embedded secret.

### Listing gate
- Accurate title, description, keywords, previews.
- Price and deliverables consistent.
- Refund/support terms clear.
- Platform requirements checked.
- Country/payout eligibility checked.

### Publication gate
- Permitted method.
- Authorization and scope.
- Owner approval when required.
- External receipt stored.
- Duplicate action prevention.

### Finance gate
- Currency and gross amount captured.
- Fees and refunds classified.
- Payout state distinguished from sale.
- Source evidence retained.
- Net contribution calculated transparently.

## 5. Prototype quality acceptance

- RIOTWORKS identity is recognizable without the logo.
- Extreme Riot + MoonWitness Comic + Industrial + Game HUD DNA is coherent.
- Both themes are intentional and accessible.
- Five core pages are high fidelity.
- Secondary pages belong to one product system.
- Character artwork is consistent and original.
- All visible interactions work.
- Demo data and simulated actions are labeled.
- No real integrations are falsely claimed.
- Desktop, tablet, and mobile layouts are usable.

## 6. Definition of done for a feature

A feature is done only when:
- The user problem and acceptance criteria are clear.
- UI and domain states are defined.
- Permission and failure behavior are specified.
- Tests cover happy path and relevant failure paths.
- Logs and audit requirements are met.
- Docs are updated.
- No unsupported product claims are introduced.
